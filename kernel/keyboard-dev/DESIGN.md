# Keyboard Device Design

## Purpose and scope

`roxy-keyboard-dev` owns `/dev/keyboard`: the character device that carries parsed key
transitions from the PS/2 keyboard driver to userspace. It defines the wire record, the bounded
queue that decouples the IRQ producer from readers, and the poll readiness that goes with it.

It does not own hardware access, scancode parsing, or key identity — those belong to
`roxy-ps2` and `roxy-key-decoder`. It does not translate keys into characters or layout symbols;
that belongs to consumers (the TTY, and the X keyboard driver in userspace).

Explicit non-goals: keyboard LEDs, key repeat, multiple keyboards, and any ioctl interface. The
device serves data through `read` only.

## The wire contract

`RoxyKeyEvent` is a 16-byte `repr(C)` record: a `CLOCK_REALTIME` timestamp in nanoseconds, the
`ROXY_KEY_*` code, the press/release flag, and two explicitly named zero fields that remove all
implicit padding.

This is a **device-serialised protocol record**, not a direct syscall ABI argument: the device
fills it and copies it into a `read` buffer, and the syscall layer never inspects its layout. It
therefore lives here rather than in `roxy-syscall` (AGENTS.md "Design and Safety"). The numeric
values are a hand-maintained contract with `sysdeps/roxy/include/roxy/keyboard-dev.h` in the Roxy
mlibc fork; both sides change together.

`keycode_to_roxy` is a single exhaustive match over `KeyCode`. That is deliberate: a new key
identity cannot be added without assigning it a stable wire value, so the contract cannot drift
silently. Losing that property is why the table is not split into per-class helpers (each match
would need a wildcard arm).

## Data flow

```
IRQ1 → roxy-ps2 scancode parser → roxy-keyboard-input::publish
     → KeyboardDevice::on_recive_input → queue → read / poll
     → (also) roxy-tty listener, unchanged
```

Registration happens at boot: `kernel-main` creates the device, registers it with devfs under the
name `keyboard`, and registers the returned listener with `roxy-keyboard-input`, keeping the
`Arc` alive for the kernel lifetime.

## Concurrency

`on_recive_input` runs in IRQ context. It takes only the queue lock, never allocates, and never
sleeps. A full queue drops its oldest record so the producer cannot block; the reader always sees
the newest input. Poll listeners are notified after the queue lock is released.

## Failure behaviour

`read` returns `EINVAL` (`FileError::BadOperation`) when the buffer cannot hold one whole record,
because splitting a record across two calls would leave userspace parsing garbage. It drains as
many whole records as fit and returns `EAGAIN` (`WouldBlock`) when nothing was queued. `poll`
reports `readable` exactly when the queue is non-empty.

## Limits

One keyboard. A second device would be added as its own node rather than multiplexed here. LED
state is not settable and not reported — there is no channel for it (see `ISSUES.md`). Key repeat
is not generated by the kernel; consumers implement it if they want it.
